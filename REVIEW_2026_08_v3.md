## Executive Summary

Every item from the v2 review has been independently verified as addressed in the current
codebase. The documentation is now substantially complete — all major features (dark mode,
decumulation, TWR/IRR/Sharpe/Sortino/Calmar, LIFO/HIFO, named goals, strategic allocation,
drift/rebalance workflow) are documented in the README with accurate descriptions. The
analytics layer is well-labelled: YTD is qualified as a balance metric, partial-year returns
carry asterisk markers, Sharpe explains negative values, and decumulation disclosures cover
pre-tax withdrawals and sequence-of-returns risk.

**Three patterns now dominate the new open findings:**

1. **Structural data not preserved on Drive sync.** `importDb()` merges only transactions
   back from local storage after a cloud overwrite. Accounts, holdings, and snapshots edited
   offline on a second device are silently replaced. This is the highest-severity finding.

2. **Touch-target compliance is still incomplete.** Icon-only buttons (`btn-icon`) are
   30 × 28 px with no breakpoint-based minimum, and `btn-sm` adds no `min-height` at the
   mobile breakpoint. Both classes fall below the WCAG 2.5.5 44 px minimum for interactive
   touch targets.

3. **A handful of financial-model edge cases and minor data-quality issues.** FEE rows
   for fully-exited holdings are discarded rather than attributed to cost basis; the forecast
   contribution model always applies equal monthly instalments regardless of the user's
   configured cadence; dividend yield uses today's portfolio value against a trailing-12 m
   income window that may have ended months ago. Each is a correctness concern rather than a
   UI cosmetic.

The app remains production-fit for its intended audience. The open items represent data
accuracy, accessibility compliance, and minor modelling precision — no UX regressions and
no correctness emergencies.

## Backend Engineering Review

### 2.1 Data Integrity & Correctness

**🟠 FEE attribution is lost when a holding is fully exited.**  
`computePD()` credits an ISIN-tagged FEE to its holding only when `target.shares > 0`
(`src/portfolio.ts:151`). Once a position is fully sold (shares fall to or below
`ZERO_THRESHOLD`), any subsequent or post-settlement FEE rows for that ISIN fall through to
the global `standaloneFees` bucket. The exited holding's cost basis and realized P&L
therefore exclude its own custody or settlement fees.  
_Fix:_ Remove the `target.shares > 0` guard for per-ISIN FEE rows. Track a per-ISIN fee
total independently of the current share count; credit the full accumulated amount to
`target.totalFees` and `target.cost` regardless of exit status.

**🟡 FX fallback silently returns the raw amount for non-base-currency transactions.**  
`toBase()` emits a `console.warn` and returns `amount` unchanged when `fxRate` is zero,
negative, or non-finite for a non-base currency transaction (`src/fx.ts:33–37`). Callers in
`portfolio.ts` (line 76) and `costbasis.ts` (line 24) cannot distinguish "correctly in base
currency" from "invalid FX, raw amount used as EUR". Silent corruption reaches cost-basis,
realized P&L, and yield figures.  
_Fix:_ Return `NaN` instead of `amount` when the rate is invalid, forcing callers to handle
the bad-data case explicitly rather than propagating a silently wrong value.

### 2.2 Import & Parsing

**🟡 `mergeTaxIntoInterest` only matches TAX rows in the identical calendar month.**  
When `profile.mergeTaxIntoInterest` is `true`, TAX rows are merged into INTEREST rows only
when both share the same `YYYY-MM` prefix (`src/import/parse.ts:402–420`). Brokers
sometimes post a tax withholding adjustment or refund in the month following the interest
payment (e.g., April TAX for March INTEREST). These cross-month TAX rows fall through as
standalone TAX transactions rather than reducing the net interest figure, overstating gross
interest income and creating orphaned TAX rows.  
_Fix:_ After the exact-month merge pass, apply an optional ±1-month lookahead for
unmatched TAX rows: find the nearest INTEREST transaction from the same source within one
calendar month and merge there, or preserve the TAX as standalone if no candidate exists.

**🟡 Profile auto-detection does not validate required columns are present.**  
`detectProfile()` scores profiles by counting how many `match.headerIncludes` hints appear
in the CSV header (`src/import/parse.ts:197–221`). A partial hit can select a profile even
when its mandatory columns (`date`, `type`, `amount`) are absent from the file. Downstream
parsing then silently produces rows with zero-value or empty fields.  
_Fix:_ After selecting the best-scoring profile, check that every column used in the
profile's `columnMap` is resolvable against the actual CSV header. If a mandatory column
(`date`, `amount`) is missing, return `null` rather than the partially-matching profile, so
the UI can ask the user to select a profile manually.

### 2.3 Sync & Conflict

**🟠 Account, holding, and snapshot edits made offline are not preserved on Drive import.**  
`importDb()` calls `mergeLocalTransactions()` to recover local-only transactions after
replacing the database with the cloud copy (`src/db/connection.ts:195–239`). No equivalent
merge exists for the `accounts`, `holdings`, `snapshots`, or `settings` tables. A user who
edits an account label or adds a snapshot on a second device while Drive has a newer copy
will silently lose those changes the next time the cloud version is accepted.  
_Fix:_ Extend the merge step to union-merge accounts and holdings by primary key (keeping
whichever row is more recently modified), and union-insert any snapshots that are present
locally but absent from the cloud copy, mirroring the transaction merge strategy.

---

### 2.4 Technical Debt

**🟢 Settings interface is still an untyped string bag.**  
`Settings` is declared as `{ [key: string]: string | null | undefined }` with a handful of
well-known keys typed only as `string?` (`src/types.ts:89–96`). Numeric settings like
`annualReturnPct` and enum settings like `calibrationInterval` have typed read-helpers in
`src/store/config.ts`, but nothing prevents writing an invalid value at the interface
boundary. Type errors in settings calls are only caught at runtime.  
_Fix:_ Narrow the well-known keys to their correct types (e.g.,
`costBasisMethod?: 'avgco' | 'fifo' | 'lifo' | 'hifo'`; `annualReturnPct?: number`) as
an incremental improvement. The index signature can remain for forward-compatible unknown
keys.

**🟢 `SPLIT` transaction `ratio` field is not validated before use.**  
Cost-basis methods apply `tx.ratio` directly to share counts and unit costs
(`src/model/costbasis.ts`). There is no check that `ratio` is a finite positive number
above a minimum threshold. A zero, negative, or non-finite ratio silently produces
`Infinity` share counts or `NaN` cost figures that propagate through the entire portfolio
calculation.  
_Fix:_ Add an early guard: if `ratio <= 0 || !isFinite(ratio)`, skip the SPLIT row and
emit a console error rather than applying a destructive transformation.

## UI/UX Design Review

### 3.1 Visual Affordance & Interaction

**🟠 Icon-only buttons (`btn-icon`) render at 30 × 28 px with no touch-target override.**  
`.btn-icon` sets `width: 30px; height: 28px` (`src/styles.css:1957–1958`). No media query
increases this size for touch screens, and no padding brings the interactive hit-area to
the WCAG 2.5.5 minimum of 44 × 44 px. These buttons appear in Settings (edit/delete for
accounts, holdings, and goals) where they are the primary action on mobile.  
_Fix:_ Add `@media (max-width: 768px) { .btn-icon { min-height: 44px; min-width: 44px;
padding: 8px; } }`. Adjust surrounding grid spacing to accommodate the larger footprint.

**🟠 `.btn-sm` receives no `min-height` override at the mobile breakpoint.**  
The `max-width: 480px` media query overrides `.btn-sm` to `padding: 5px 10px; font-size: 11px`
(`src/styles.css:1774–1777`), yielding approximately 21–23 px of rendered height.
Transaction ledger delete and edit buttons use this class exclusively on small screens,
putting them below the 44 px WCAG 2.5.5 touch-target guideline.  
_Fix:_ Add `min-height: 44px; padding: 10px 12px;` to the `.btn-sm` rule in the `max-width: 480px`
block.

### 3.2 Accessibility

**🟡 Companion chart data tables are not reachable by keyboard or screen-reader navigation.**  
Chart canvases reference their companion data tables via `aria-describedby`
(`src/template.ts:72, 109` and equivalent). However, the companion tables are rendered with
the HTML `hidden` attribute, making them invisible to both sighted keyboard users and
assistive technology. A screen reader receives the `aria-describedby` reference but cannot
follow it to an element that is `hidden`.  
_Fix:_ Replace `hidden` with `class="sr-only"` (visually hidden but DOM-present) so that
`aria-describedby` resolves to accessible content, or add a visible "View data table"
button that toggles the table's visibility for all users.

**🟡 Conditional form sections do not announce visibility changes to assistive technology.**  
Dialogs in `src/ui/accountDialog.ts`, `holdingDialog.ts`, and `transactionDialog.ts`
show and hide input groups (e.g., the locked-account fields, the security autocomplete)
by toggling CSS display without any `aria-live` region or focus management. A screen-reader
user who enables the "Primary investment account" checkbox hears the checkbox toggle but
receives no announcement that new fields have appeared beneath it.  
_Fix:_ Wrap each conditional section in a container with `aria-live="polite"`. Alternatively,
move focus to the first newly revealed input after the toggle so the screen reader naturally
reads the new content.

### 3.3 Mobile

**🟡 Transaction ledger columns may truncate on viewports narrower than 360 px.**  
`#tx-ledger-list` uses `grid-template-columns` with `minmax()` expressions
(`src/styles.css:781–792`). On handsets with 320–350 px viewports (still common in emerging
markets), the ISIN and name columns, which are always visible, can truncate to a few
characters without any overflow indicator. The `data-mobile-hidden` columns are suppressed,
but the remaining columns still receive fractional widths that can become too narrow to read.  
_Fix:_ Add a `max-width: 360px` breakpoint that further reduces column widths or switches
the ledger to a stacked single-column card layout (one card per transaction row).

---

### 3.4 Empty & Loading States

**🟡 The Analytics tab has no loading indicator during metric computation.**  
Switching to the Analytics tab triggers synchronous computation of TWR, IRR, XIRR,
Sharpe, Sortino, Calmar, volatility, and drawdown across the full snapshot history. On
portfolios with several years of monthly data, this can produce a perceptible delay during
which the section appears frozen. There is no spinner or "Computing…" placeholder.  
_Fix:_ Render a lightweight skeleton (placeholder tiles matching the KPI grid layout)
immediately when the Analytics section becomes active, then replace it with computed results
on the next microtask tick using `requestAnimationFrame` or `setTimeout(fn, 0)`.

**🟡 CSV import has no progress indicator between file selection and preview rendering.**  
After the user selects a file, `parseWithProfile()` runs synchronously on the full CSV
content (`src/main.ts` import flow). For files with 500+ rows the UI is unresponsive for
100–300 ms with no visual feedback. The user has no indication whether the app is working
or stalled.  
_Fix:_ Show a "Parsing file…" spinner or inline text immediately on `change` before
invoking the parser; hide it when the preview panel renders.

---

### 3.5 Information Architecture

**🟢 Settings cards are an undivided vertical scroll.**  
`renderSettings()` emits eight card sections in sequence (Accounts, Holdings, Contributions,
Cost-basis, Goals, Alerts, Analytics, Rules) with no grouping headers or collapsible regions
(`src/views/settings.ts`). For a new user the scroll communicates no dependency order: they
must add an account before adding holdings, and holdings must exist before the drift table
works. This ordering is not surfaced visually.  
_Fix:_ Group cards under three section headings — "Portfolio structure" (Accounts, Holdings),
"Tracking & planning" (Contributions, Goals), "Advanced" (Cost-basis, Analytics, Alerts,
Rules) — and add a one-line context note at the top of "Portfolio structure" explaining
that accounts are the starting point.

**🟢 "Add data" nav label remains ambiguous for first-time users.**  
The tab renders as "Add data" (`src/template.ts:51`) with an `aria-label` of
"Add data (add snapshot or import CSV)". Sighted users on desktop see a tooltip only on
hover; mobile users never see the qualifier. The label does not signal that this is where
monthly net-worth updates are recorded, which is the first step a new user needs to take.  
_Fix:_ Change the visible label to "Log data" or "＋ Log" and update the `aria-label`
accordingly. The prior "Log" name was more descriptive; the rename to "Add data" moved away
from clarity.

## Wealth Management Review

### 4.1 Analytics Correctness

**🟡 Dividend yield divides trailing-12 m income by today's portfolio value, not by the
average value during the income period.**  
`dividendMetrics()` computes `yieldPct = trailing12m / currentPortfolioValue`
(`src/model/insights.ts:693`). The trailing-12 m income window is anchored to the
latest _imported transaction month_, which may be several months in the past. The denominator
is the portfolio's market value _today_. If the portfolio has grown substantially since the
last import, the yield appears lower than the income was actually earning during that period;
if it has declined, the yield appears inflated.  
_Fix:_ Add a date qualifier to the yield tile: "Yield (as of last import: YYYY-MM)" so the
user understands the income window. As an improvement, divide by the average of start and
end portfolio values bracketing the 12 m period rather than today's value.

### 4.2 Forecasting & Retirement Planning

**🟠 Forecast applies equal monthly contribution instalments regardless of the user's
configured contribution cadence.**  
`forecastMultiAccountSeries()` divides `annualContrib` by 12 and adds it every month
(`src/model/forecast.ts:165`). `annualContrib` is derived from `getMonthlyContribBudget() × 12`
(`src/views/networth.ts:97`), which already normalises the user's chosen cadence to a
monthly equivalent. The round-trip is mathematically correct for totals but the timing model
always drips contributions evenly each month rather than once per quarter (or per the
configured interval). For a user who invests quarterly, the forecast overestimates early
compounding by crediting three phantom monthly deposits before the first real lump appears.  
_Fix:_ Pass the configured `contributionInterval` through to `forecastMultiAccountSeries()`
and apply the contribution only in months that fall on the correct interval boundary. Add an
explanatory note in the forecast card: "Contributions modelled as [interval]; monthly totals
are preserved but may land in different months than shown."

**🟡 Retirement corpus projection provides no scenario or sensitivity context.**  
The accumulation forecast feeding the retirement corpus uses a single fixed annual return
per account (`src/views/networth.ts:91–101`). The displayed corpus figure (e.g., "€ 850 000
by 2044") carries no range or confidence band. A user who retires during a bear market could
see a corpus 30–40 % lower than the deterministic figure and be surprised that the model
gave them no warning.  
_Fix:_ Add a tooltip or footnote beneath the corpus figure: "Projection uses your configured
annual return of X %. A market downturn in the years approaching retirement could materially
reduce the available balance. Consider running the forecast with a more conservative return
to see the lower bound."

**🟡 Decumulation return-rate manual override is not visually distinguished from the
auto-derived value.**  
The drawdown return rate input is auto-derived as a value-weighted average of account
returns on first render (`src/views/networth.ts:1066–1076`). If the user edits the field,
`_ddReturnPctManual` is set to `true` and the override is persisted via `setSetting()`.
However, the input field looks identical in both states: a plain number input with no label
change, no badge, and no "reset to auto" affordance. After a session reload, a user cannot
tell whether the figure they see was computed from their account configuration or was set
manually weeks ago.  
_Fix:_ When `_ddReturnPctManual === true`, append a "Manual override" badge next to the
input (e.g., "⚙ Manual — click to reset") and add a reset-to-auto button that clears the
stored setting and re-derives the value from accounts.

### 4.4 Financial Model Gaps

**🟡 FEE rows for a fully-exited holding are silently absorbed into the global fee
bucket, distorting realized P&L.**  
This is the financial consequence of the backend issue noted in §2.1. When a user sells a
full position and later receives a custody-fee confirmation tagged to that ISIN, the fee is
not deducted from the holding's cost basis because `target.shares > 0` is false
(`src/portfolio.ts:151`). The exited holding's realized P&L is therefore overstated by the
fee amount. For a 0.15 % annual TER on a €20 000 position sold mid-year, the fee omission
is on the order of €15 — small but visible against a modest gain.  
_Fix:_ See §2.1. Remove the `shares > 0` guard for ISIN-tagged FEE rows.

## Cross-Cutting Themes

### T1: Structural sync merge is transaction-only

The local-first architecture relies on `mergeLocalTransactions()` to recover edits after a
cloud overwrite. Adding the equivalent for accounts, holdings, and snapshots (insert
local-only rows, log conflicts on key collisions) would make the merge complete and extend
the robustness that already exists for the transaction table.

### T2: Touch-target compliance needs a targeted audit pass

Two distinct button classes (`btn-icon`, `btn-sm`) fall short of the 44 × 44 px WCAG
minimum for interactive touch targets, and both issues can be resolved with four CSS rules.
A deliberate mobile pass reviewing all interactive elements against WCAG 2.5.5 would close
both findings and any remaining edge cases in a single PR.

### T3: Financial model disclosures are strong; edge-case correctness is the remaining gap

The prior review cycle improved disclosures substantially (SoRR caveat, pre-tax withdrawal
note, balance-vs-investment qualifiers, Sharpe negative-value explanation). The remaining
open items are narrower data-accuracy issues: a FEE attribution edge case, a yield
denominator timing note, and a contribution cadence simplification. These do not affect
typical single-account accumulation users but surface as small errors for users who sell
positions or check income analytics closely.
