## Executive Summary

Wealth Tracker is a well-engineered, actively-maintained **personal tracker** for a disciplined
ETF accumulator with simple, mostly-EUR accounts. The codebase is clean, the test suite is real,
and the analytics are genuinely ahead of a typical side project. Where it falls short is the gap
between what it measures and what it _should_ measure, and between what the docs claim and what
the code delivers.

**Three patterns dominate every panel:**

1. **Net-worth snapshots are used as a proxy for investment performance.** All performance,
   risk, and income metrics run on total account balances, not on a clean investable return
   series. This inflates apparent results for contributors and deflates them for drawers.

2. **Multi-currency is a stub, not a feature.** `currency` and `fxRate` are stored but never
   applied. `fmt()` is hard-coded to EUR. Any user with CHF, USD, or GBP assets is getting
   materially wrong numbers, silently.

3. **The app is optimised for accumulation, not for a 30-year lifecycle.** Decumulation,
   tax planning, pension structure, liabilities, inheritance, and retirement draw-down are
   absent from both the data model and the UX.

The app is **fit for use today** by its intended audience. It is **not yet fit for 30 years** in
its current form without significant work on the data model, performance measurement, and UX trust.

## Backend Engineering Review

> Validation: `yarn test`, `yarn typecheck`, and `yarn build` all pass. The concerns below are
> about correctness, durability, and long-term design — not current CI breakage.

### 2.1 Data Integrity & Correctness

**🔴 Same-day transaction ordering is not durable.**
`loadTransactions()` orders only by `date` (`src/db/repositories/transactions.ts:16–20`), while
`computePD()` explicitly assumes that same-day order is preserved (`src/portfolio.ts:21–25`). FIFO
cost basis and split handling become nondeterministic after a DB reload for any same-day
BUY/SELL/SPLIT sequence.

**🔴 Oversells are silently mis-computed.**
`computeAvgCost()` subtracts `sharesSold` even when it exceeds the held lot and then clamps to
zero (`src/model/costbasis.ts:33–50`). `computeFIFO()` partially consumes lots and prorates
proceeds instead of raising an error for impossible sells (`src/model/costbasis.ts:97–124`). The
result is wrong realized P&L with no warning.

**🔴 TWR and risk analytics are materially misleading.**
`twr()` expects external cash-flow adjustments (`src/model/insights.ts:37–53`), but analytics
passes `pd.monthly`, which contains only BUY outflows (`src/views/analytics.ts:145`,
`src/portfolio.ts:70–77`). Volatility, drawdown, Sharpe, and Sortino also all run on raw net-worth
snapshots (`src/model/insights.ts:157–206`). Deposits, withdrawals, pension contributions, and
skipped months distort every "performance" metric.

**🟠 Standalone `FEE` transactions are ignored.**
`TxType.FEE` exists and Trade Republic imports it (`src/import/profiles/trade_republic.ts:40`),
but `computePD()` never handles `FEE` rows (`src/portfolio.ts:65–135`). `totalFees` therefore
excludes broker/custody fees unless embedded in BUY/SELL rows.

**🟠 FX is stored but never applied.**
`currency`/`fxRate` are persisted (`src/types.ts:33–34`, `src/db/schema.ts:29–30`) but no
calculation in `src/model/costbasis.ts` or `src/portfolio.ts` uses them. All amounts are treated
as EUR regardless of the stored currency.

**🟡 XIRR is numerically fragile.**
`xirr()` uses a single-start Newton solve with no bracketing fallback
(`src/model/insights.ts:552–570`). Long or irregular cash-flow histories with multiple IRR roots
can silently return `null`.

**🟡 Income analytics over-count in edge cases.**
`dividendMetrics()` uses `Math.abs(tx.amount)`, so broker corrections and reversals become
positive income (`src/model/insights.ts:459–462`). Trailing-12m and YoY are anchored to
wall-clock `new Date()`, not to the last imported date, so stale portfolios drift in income KPIs
without any new data.

### 2.2 Database Design

**🔴 Deleting an account silently rewrites history.**
Snapshots store dynamic account keys in a JSON blob (`src/db/schema.ts:72–77`,
`src/db/repositories/snapshots.ts:24–33`). `snapTotal()` sums only keys present in the current
config (`src/utils.ts:4–10`). Deleting an account makes every historical total smaller. The UI
message claiming "Historical data is not affected" (`src/views/settings.ts:415–416`) is false.

**🟠 Transactions are not linked to accounts.**
`Transaction` and the `transactions` table have a `source` string but no `accountId`
(`src/types.ts:20–35`, `src/db/schema.ts:17–33`). This blocks per-account IRR, internal transfer
modeling, and tax-lot segmentation by account.

**🟡 JSON snapshot blobs trade simplicity for weak integrity.**
`snapshots.values_json` avoids schema churn but gives no foreign keys, no per-account
constraints, no SQL queryability, and no safe migration path if account structure changes over
decades.

**🟡 Every write is a full-database rewrite.**
Each save exports the whole SQLite DB to IndexedDB (`src/db/connection.ts:154–173`), and sync
uploads the entire DB file (`src/sync/drive.ts:139–199`). The separate cache store duplicates
transactions and snapshots (`src/cache/db.ts`). Storage and bandwidth scale poorly compared to
actual data volume.

---

### 2.3 Import & Parsing

**🟠 Built-in split support is incomplete.**
`TxType.SPLIT` exists and cost basis handles it (`src/model/costbasis.ts:25–32,87–95`), but the
Trade Republic profile does not map `STOCK_SPLIT` corporate-action rows
(`src/import/profiles/trade_republic.ts:33–47`). These rows arrive as unknown types and are
silently ignored.

**🟠 Import merge is append-only; corrections are never reconciled.**
`mergeTransactions()` uses `INSERT OR IGNORE` (`src/db/repositories/transactions.ts:25–40`).
Broker corrections, deletions, or amended amounts in a re-import are ignored.

**🟡 Bad numbers are silently coerced to zero.**
`parseNumber()` returns `parseFloat(...) || 0` (`src/import/parse.ts:56–69`). Malformed amounts
become valid zero-value transactions with no warning to the user.

**🟡 Profile matching is brittle.**
Column lookup is exact-string only (`src/import/parse.ts:219–225`). Only two built-in profiles
exist, and custom profiles built via `buildProfileFromMapping()` are not persisted anywhere
(`src/import/profile.ts:15–34`).

---

### 2.4 Sync & Backup

**🔴 Conflict handling is "newer file wins" with partial local merge only for transactions.**
`pullFromCloud()` replaces the local DB if the cloud timestamp is newer (`src/sync/engine.ts:55–86`).
`importDb()` only merges back local-only transactions (`src/db/connection.ts:201–217,241–262`),
not snapshots, settings, accounts, or holdings. Offline edits on a second device can be
permanently lost.

**🟠 Drive version tracking is implemented but unused.**
`setDriveVersion()`/`getDriveVersion()` exist (`src/db/repositories/meta.ts:63–70`) but nothing
reads the stored version. Real conflict detection requires it.

**🟠 Backup validation is shallow.**
`validateBackup()` checks only top-level shape (`src/backup/exportImport.ts:67–85`), not field
types, finite numbers, enum values, or date formats. A corrupted backup passes silently.

**🟠 Backup preview is an XSS surface.**
`summarizeBackup()` returns raw HTML from backup content (`src/backup/exportImport.ts:88–132`).
`confirmDialog()` accepts `bodyHtml` as unescaped markup (`src/ui/confirmDialog.ts:9–10,24–27`),
and restore passes it straight through (`src/main.ts:818–820`). A crafted backup file could inject
arbitrary HTML/JS.

**🟡 Drive file selection is nondeterministic if duplicates exist.**
`findDbFile()` returns `files[0]` with no tie-break or deduplication
(`src/sync/drive.ts:90–107`).

---

### 2.5 Doc Accuracy vs Code Reality

**🔴 legacy report doc overstates sync safety.**
It says local SQLite is authoritative and Drive is "not the source of truth" (`legacy report doc:379`),
but boot sync always pulls cloud first if the cloud timestamp is newer
(`src/main.ts:597–600`, `src/sync/engine.ts:55–86`).

**🔴 legacy report doc claims `foldInto` has an implemented code path — it does not.**
The field exists in types and config (`src/types.ts:74`, `src/views/settings.ts:706–707`) but
there is no computation path in `src/model/*` or `src/portfolio.ts`.

**🔴 legacy report doc says cost basis handles edge cases well — oversell handling disproves this.**
`src/model/costbasis.ts:33–50,97–124` silently produces wrong numbers on impossible sells.

**🟡 legacy analytics doc is inconsistent about the analytics gating threshold.**
The doc says advanced analytics are gated at 24+ months (`legacy analytics doc:71`); the code uses
12 months (`src/views/analytics.ts:293–295`).

**🟡 legacy analytics doc still lists Passive Income Projection as "Add".**
legacy report doc acknowledges it was removed; the design doc was never updated.

**🟡 legacy analytics doc says "all calculations rely exclusively on monthly snapshots".**
This is wrong: cost basis, IRR, dividends, and drift all derive from transactions and config, not
snapshots.

---

### 2.6 Technical Debt

**🟠 Cache fingerprinting is unsafe.**
The cache key uses only array length plus first/last row serialization lengths
(`src/cache/db.ts:20–28`). Middle-row changes or same-length edits bypass cache invalidation,
causing stale boot reads (`src/main.ts:550–577`).

**🟡 Analytics assume perfect monthly continuity.**
Volatility, drawdown duration, rolling CAGR, and TWR treat each consecutive snapshot pair as
exactly one month apart (`src/model/insights.ts:157–175,194–206,343–355`), even when months
were skipped.

**🟢 Type looseness is widespread.**
`Transaction.type` is `string` (`src/types.ts:25`); settings are string bags
(`src/types.ts:89–93`). Many calculations depend on string conventions rather than typed
invariants, making future refactors risky.

---

### 2.7 Security

**🟡 Financial data leaves the browser as raw plaintext.**
Drive sync uploads the entire SQLite file to Google Drive AppData
(`src/sync/drive.ts:113–199`), and backup/export writes full plaintext JSON. No app-level
encryption exists.

**🟠 Backup-import XSS** is the most concrete app-side security issue (see §2.4 above).

---

### 2.8 Testing Gaps

The existing test suite is meaningful, but it covers the happy path. Missing coverage:

- Oversells and negative-lot handling in cost basis
- Same-day ordering after DB reload
- Standalone `FEE` rows in portfolio totals
- Split import mapping from built-in profiles
- Cache fingerprint collisions (middle-row changes)
- Multi-device sync conflicts
- Backup-import XSS with a crafted payload
- Multi-currency conversion paths
- Irregular snapshot spacing in analytics metrics

## UI/UX Design Review

> The app has real strengths — a CSS design-token system, dark mode, and thoughtful empty-state
> copy — but is well behind Empower, Copilot Money, Monarch, Sharesight, and Portfolio Performance
> in clarity, trust, accessibility, and long-term durability.

### 3.1 Information Architecture

**🔴 The top-level nav is not intuitive.**
`appTemplate()` splits the app into **Net Worth / Portfolio / Analytics / Settings / Log**, but
"Net Worth" and "Analytics" overlap heavily. Contributions and Dividends are buried as Portfolio
subviews. A new user cannot naturally infer where "returns," "income," or "performance" live.

**🔴 There is no transaction ledger UI.**
`renderLog()` shows only import status and snapshot history. Imported transactions are not
inspectable in a browsable list. This is a major trust gap versus Sharesight, Monarch, and
Portfolio Performance.

**🟠 "Log" is overloaded and mislabeled.**
The Log section contains sign-in, CSV import, monthly snapshot entry, and history
(`src/views/log.ts`). Best-in-class tools separate activity history from data-entry forms.

**🟠 Onboarding covers only a partial path.**
`renderSetupBanner()` tracks Sign in → Add accounts → First monthly update. It omits importing
transactions and configuring holdings, even though the Portfolio, Contributions, and Dividends
tabs all depend on those steps.

**🟡 Some empty-state CTAs create extra hops.**
`nw-empty` and `an-empty` push to `data-goto="log"`, but `renderSnapForm()` then tells users "No
accounts configured yet" and redirects to Settings — a preventable second redirect.

**🟡 Settings is an admin panel, not a guided experience.**
`renderSettings()` injects ten cards sequentially. That works for power users but is not
approachable for consumer-grade onboarding.

---

### 3.2 Visual Design System

**🟠 The design system exists but is not authoritative.**
`src/styles.css` defines tokens, yet `src/template.ts` alone contains 75 inline `style="..."`
usages. This weakens consistency and makes long-term UX evolution fragile.

**🟠 Typography is too small for financial software.**
`.card-title`, `.kpi-label`, and `.note` are `11px`; mobile rules reduce these to `10px`/`9px`.
Premium finance apps (Empower, Monarch) use 13–14px as the minimum for data labels.

**🟡 `src/theme.ts` duplicates token logic.**
`T` / `resolvedT()` mirror only part of `:root`, increasing the risk of visual drift between CSS
surfaces and Chart.js canvases.

**🟡 Desktop real estate is underused.**
`body { max-width: 940px }` is readable for prose but suboptimal for data-dense portfolio tables
and charts.

**🟡 Dark mode is OS-only.**
`@media (prefers-color-scheme: dark)` is supported but there is no user-level toggle in the UI.

---

### 3.3 User Flows

**🔴 CSV import auto-confirms on clean files, bypassing review.**
In `src/main.ts`, clean imports where `summary.unmapped.length === 0 &&
summary.dateErrors.length === 0` skip the review step and call `confirmImport()` immediately. For
financial data this removes the most important trust checkpoint.

**🟠 There is no manual transaction entry.**
The Log view offers only CSV import and monthly snapshots. There is no way to add, edit, or
delete a single transaction. Compared to Portfolio Performance or Sharesight, this is a serious
workflow gap.

**🟠 Snapshot entry lacks validation and reconciliation.**
`renderSnapForm()` accepts free-form totals without cross-checking against imported transactions
or guiding the user through account-by-account balance confirmation.

**🟡 Users must assemble mental models across screens.**
Accounts are in Settings, transactions are in CSV import, holdings metadata is in Settings,
and derived insight is scattered across Portfolio and Analytics. Market leaders collapse this into
guided, contextual flows.

---

### 3.4 Data Density vs Comprehension

**🟠 Analytics packs too much without hierarchy.**
`renderAnalytics()` fills `#an-kpis-l1`, `#an-kpis-l2`, and `#an-kpis-risk` with dense KPI tiles
using advanced jargon. Copilot and Monarch are significantly better at staging insight progressively.

**🟠 Row expansion has weak affordance.**
`.hold-row` and `.snap-row-compact` expand on click with no strong visual cue (no chevron, no
`aria-expanded`, no hover state that clearly communicates expandability).

**🟡 Charts dominate without accessible table mirrors.**
Core data is in Canvas elements (`c-nw-hist`, `c-an-growth`, `c-an-drawdown`, etc.) with no
equivalent structured data tables for accessibility or export.

**🟡 The monthly heatmap is fragile on touch.**
`_renderHeatmap()` in `src/views/analytics.ts` uses tiny cells, intensity-coded colors, and
`title` hover text. That degrades on touch devices and small screens.

---

### 3.5 Empty / Loading / Error States

**🟢 Top-level empty states are present and reasonable.**
`nw-empty`, `port-empty`, `an-empty`, and `auth-prompt` are better than bare blanks.

**🟠 Dividends has no true "no income data" empty state.**
`renderDividends()` only checks `!!pd`; if portfolio data exists but no dividends, `div-empty` is
hidden and the user gets a weak zero-value table instead of a purposeful empty state.

**🟡 Empty-state quality is inconsistent.**
Contributions and Dividends empty states are noticeably thinner than Net Worth and Analytics.
Some are icon + button only.

**🟡 Loading/error handling is coarse.**
`renderSection()` uses a generic spinner and a generic error block. No per-widget skeletons or
nuanced degraded states exist.

---

### 3.6 Accessibility

**🔴 Key interactions are mouse/touch-only.**
`.hold-row`, `.snap-row-compact`, and `.annual-row` expand on click but are not keyboard-focusable
and have no `aria-expanded`. There is no keyboard alternative.

**🔴 Focus treatment is removed or absent.**
`.form-input` sets `outline: none`. Buttons have no dedicated focus styles. `.info-tip:focus`
removes outline. This is a serious barrier for keyboard navigation.

**🟠 Dialogs do not fully trap focus.**
`confirmDialog()` and `showSigninOverlay()` restore focus on close but do not trap it while open.
`confirmDialog()` also confirms on global Enter regardless of which element is focused — a
trigger-happy confirmation risk.

**🟠 Charts are inaccessible to screen readers.**
Core data visualizations are `<canvas>` elements with no meaningful alternative narration or
structured data equivalents.

**🟡 Tooltips are hover-centric.**
`infoTip()` and `attachEtfPopovers()` rely on `title` or custom popovers that are weak for
screen readers and touch.

---

### 3.7 Mobile

**🟠 Touch targets are too small.**
At `max-width: 480px`, `.nav button` drops to `min-height: 36px` with `font-size: 11px` — below
the ergonomic standard for a finance app.

**🟠 Mobile hides too much data.**
`.hold-grid` collapses to 3 columns at `max-width: 599px`; the rest goes into an expansion panel.
Scanability is significantly reduced on phones.

**🟡 The heatmap is technically responsive but not truly mobile-friendly.**
`overflow-x: auto` with a minimum-width table is a desktop fallback, not a mobile-native
representation.

---

### 3.8 Missing UX Promised in Docs

**🟠 legacy analytics doc promised sparklines that are not present.**
The wireframes specify Total Portfolio Value + sparkline and Monthly P&L 12-bar sparkline;
`renderAnalytics()` ships plain KPI tiles.

**🟠 legacy analytics doc promised an Annual Returns table with bar sparklines.**
The current UI has a heatmap only, not a structured annual-return table.

**🟡 Currency and broker/institution allocation views are missing.**
`_renderAllocationDonuts()` only renders account, asset-class, and region views — not currency
or institution.

**🟡 Dividend projection was explicitly removed (legacy report doc) without a stated replacement.**
Income investors are left with no projection surface.

---

### 3.9 30-Year UX Durability

**🔴 The product is operationally tied to Google Drive sign-in.**
`auth-prompt` communicates that data is stored in Google Drive. `renderSettings()` blocks
configuration when signed out. If Google changes its OAuth policies or Drive API terms, the app
loses its primary storage layer.

**🟠 The UI architecture will be hard to evolve over decades.**
Large template strings, 75+ inline styles, and a 2,047-line CSS file can work now but are not
a durable foundation for iterative UX improvement over 30 years.

**🟠 The asset model is too narrow for a lifetime.**
Users' wealth broadens over time (real estate, pensions, business equity, inheritance). The
ISIN-centric model can't grow with them without significant data model changes.

---

### 3.10 Competitive Gaps

**🔴 vs Empower / Monarch / Copilot / YNAB:**
No automatic account aggregation, no budgeting or cash-flow layer, no liabilities/debt, no
spending categorization, no recurring bill tracking.

**🔴 vs Sharesight / Portfolio Performance:**
No benchmark comparison UX, no transaction ledger, no tax reporting exports, no multi-currency
UX, no corporate-action handling visible to the user.

**🟠 vs premium wealth tools generally:**
No polished "trust surfaces" — import review, auditability, drilldown, portfolio explanations,
and scenario planning all feel thinner than the market leaders.

## Wealth Management Review

> This panel assesses financial model correctness and fitness for a sophisticated European
> individual investor (Swiss/German context implied by N26 and Trade Republic profiles).

### 4.1 Financial Model Completeness

**🔴 The base currency is not modeled.**
`fmt()` is hard-coded to `currency: 'EUR'` (`src/utils.ts:16–21`). For CHF/EUR/USD portfolios
this can materially misstate cost basis, gains, and allocation. (Confirmed by backend panel:
`fxRate` is stored but never applied.)

**🔴 The asset model is security-centric, not wealth-centric.**
`Holding` requires an ISIN and is validated by `ISIN_RE`. Account types are limited to
investment/savings/pension/avd/cash. There are no liabilities, mortgages, private equity, direct
real estate, crypto wallets, collectibles, trusts, or household entities.

**🟠 `Snapshot` is too thin for 30-year planning.**
`{ date, [accountKey]: number }` records balances, not economic structure. No debt
amortization, tax wrapper, legal owner, beneficiary, or pension-regime metadata.

**🟡 Portfolio classification is shallow.**
`Holding` has `assetClass`, `region`, `acc`, `ter` but no fund domicile, benchmark, factor style,
sector, currency exposure, hedged/unhedged flag, duration, or wrapper/tax status.

---

### 4.2 Performance Measurement Correctness

**🔴 Most "returns" are balance-growth metrics, not investment-performance metrics.**
`cagr()`, `totalReturn()`, `ytdReturn()`, and `annualReturns()` all use `snapTotal()` of total
net worth. That mixes investment performance with savings deposits, pension contributions, cash
buildup, and manual revaluations.

**🔴 TWR is not a clean time-weighted return for multi-account portfolios.**
Analytics passes `pd.monthly` (BUYs only) as the cash-flow adjustment to `twr()`. Deposits,
withdrawals, sell proceeds, and pension cash flows are not neutralized.

**🔴 XIRR cash-flow construction is incomplete.**
Analytics builds IRR from BUY outflows plus one terminal value. SELL proceeds are not modeled as
inflows. For anyone realizing gains or rebalancing, IRR overstates skill.

**🟠 No benchmark or attribution.**
legacy analytics doc correctly says benchmark comparison is out of scope given no external data provider.
However, this means the app cannot answer the core investor question: "Did I beat my passive
alternative?"

---

### 4.3 Risk Metrics

**🔴 Risk metrics measure household-balance volatility, not portfolio risk.**
Volatility, max drawdown, Sharpe, Sortino, and Calmar all derive from `snapTotal(snaps)`, which
includes cash, savings, and contribution flows. This systematically understates investment risk.

**🔴 Sequence-of-returns risk is discussed, not modeled.**
legacy analytics doc presents Calmar as valuable for FIRE. Without a decumulation engine, spending path,
or Monte Carlo, this is not real retirement sequence-risk analysis.

**🟠 Monthly snapshots cap analytical depth.**
No intra-month drawdown, stress testing, correlation matrix, or tail-risk analysis is possible.
All metrics treat each snapshot pair as exactly one month (see backend finding §2.6).

**🟠 Inflation is a display deflator, not a real-returns model.**
`_deflateByInflation()` divides nominal forecasts by a constant rate. That is a rough overlay,
not a real-returns calculation.

**🟡 Risk metrics appear with very short history.**
Volatility starts after 3 snapshots; drawdown after 2. These numbers are almost always noise at
that scale.

---

### 4.4 Retirement / FIRE Planning

**🔴 Forecasting is deterministic accumulation, not retirement planning.**
`forecastMultiAccountSeries()` compounds at a fixed rate with fixed contributions. No withdrawals,
taxes, glide path, pension income, annuitization, mortality, or spending shocks.

**🔴 Goals count locked assets as available.**
Goal progress uses `snapTotal(latestSnap)` and ETA uses all `accountInputs`, while
`locked`/`lockedUntil` are only displayed as a separate KPI. A house-deposit goal incorrectly
counts inaccessible pension assets as progress.

**🟠 Forecast horizon is capped at 20 years.**
`FORECAST_RANGE_LABELS` exposes 5/10/20 years (`src/constants.ts:23–27`). Wealth planning
routinely needs 30–50 year horizons.

**🟠 Swiss/German retirement specifics are absent.**
No pillar structure, tax-deductible contribution caps, conversion rates, AVS/AHV, occupational
pensions, vesting, or withdrawal ordering.

---

### 4.5 Tax Considerations

**🔴 Not adequate for real tax filing.**
`tax` is a plain number with no jurisdiction, treaty status, tax-lot holding period, reclaimable
withholding, or account wrapper metadata.

**🔴 Multi-currency tax accounting is broken for non-EUR assets.**
Since `fxRate` is stored but not applied, realized gains and cost basis are wrong in any
jurisdiction that taxes in base currency.

**🟠 Cost basis methods are limited.**
Only `avgco` and `fifo` are supported. No LIFO, specific identification, HIFO, or
jurisdiction-aware method control.

**🟠 Dividend/interest tax handling is aggregation, not tax reporting.**
`computePD()` tracks `taxPaid` and `taxBySource`, but does not distinguish domestic withholding,
foreign withholding, refundable credits, or separate national tax boxes.

---

### 4.6 Income Analytics

**🔴 Dividend Yield is mis-denominated.**
`_renderIncomeAnalytics()` passes `currentPortfolioValue = total`, where `total` is total net
worth from `snapTotal()`. `dividendMetrics()` divides income by that value. Cash, savings,
pension, and other assets dilute the yield, making it meaningless as a financial ratio.

**🟠 Income metrics drift with wall-clock time.**
`dividendMetrics()` uses `new Date()` for trailing-12m and YoY. If the user stops importing
data, income KPIs change autonomously without new data.

**🟠 Income is blended.**
`dividendMetrics()` combines `DIVIDEND` and `INTEREST`. This is convenient but insufficient for
serious income analysis or tax reporting.

---

### 4.7 Asset Allocation & Drift

**🟠 Drift targets are derived from contribution weights, not strategic allocation.**
`computeDrift()` derives target weights from annualized contribution weights of active holdings.
That is useful for DCA control but is not a full wealth-allocation framework. A user who stops
contributing would have a broken drift view.

**🟠 Actual weights can fall back to cost basis.**
If per-ETF snapshot market values are absent, `computeDrift()` uses `pos.cost`
(`src/model/drift.ts:58–61,89–90`). After strong price moves, cost basis can be very wrong as
a proxy for market weight.

**🟡 Allocation dimensions are thin.**
Missing: duration, factor exposure, tax-wrapper, liability-matching, and household-balance-sheet
views.

---

### 4.8 Behavioral Finance

**🟢 The manual monthly-snapshot design is behaviorally healthy.**
It naturally reduces compulsive checking versus live-price apps that amplify myopic loss aversion.

**🟠 The analytics roadmap leans toward engagement over discipline.**
legacy analytics doc labels "Monthly Return Heatmap" as "high engagement" and "Waterfall chart" as
"cosmetic, visually engaging." For long-horizon investors, these can encourage return-chasing and
benchmark anxiety.

**🟡 Risk tiles can look more authoritative than the data warrants.**
With sparse monthly snapshots, a polished Sharpe ratio or Max Drawdown tile may anchor users on
noisy estimates.

---

### 4.9 Multi-Currency & International

**🔴 The app is EUR-only in practice.**
`fmt()` hard-codes EUR. `fxRate` is stored but never used. This is the largest correctness
issue for Swiss/German cross-border investors.

**🟠 Trading currency ≠ economic currency exposure.**
legacy analytics doc proposes "Currency Allocation" from `Transaction.currency`. That is financially
wrong: buying a global ETF denominated in USD does not create USD economic exposure.

**🟠 No hedging metadata.**
No way to distinguish CHF-hedged vs EUR-unhedged bond funds, which is material for European
multi-currency portfolios.

---

### 4.10 Docs vs Financial Reality

**🔴 legacy analytics doc overstates what monthly snapshots can support.**
TWR, volatility, Sharpe, Sortino, and heatmaps are all built on household net-worth snapshots,
not on a clean investable return series. The metrics are presented without this caveat.

**🔴 The currency-allocation plan in legacy analytics doc is conceptually wrong.**
Deriving FX exposure from `Transaction.currency` would mislead users about true economic
currency risk.

**🔴 legacy report doc overstates sync safety and cost-basis robustness** (see backend findings §2.4
and §2.5).

---

### 4.11 30-Year Financial Durability

**🔴 The app does not support a retirement lifecycle.**
No decumulation, inheritance, divorce, philanthropy, estate transfer, changing tax residence,
liabilities, or household-level planning. It is built entirely for accumulation.

**🟠 The data model handles accumulation but not decumulation.**
Fine for a young ETF saver; inadequate for someone 10 years from or in retirement.

**🟠 Corporate-action durability is partial.**
`SPLIT` is modeled, but not spinoffs, rights issues, share-class changes, fund domicile
changes, or complex mergers.

**🟠 Inflation, currency, and legal/tax regime changes are not durable objects.**
For a 30-year Swiss/German investor, these are central planning variables, not edge cases.

## Cross-Cutting Themes

These patterns emerged independently across all three reviews and represent the deepest
structural issues:

### T1 — Net-worth snapshots are used as investment-performance proxies

All three panels identified the same root problem: performance metrics (CAGR, TWR, XIRR,
volatility, Sharpe) run on `snapTotal()` of all account balances, including cash contributions,
savings, and pension. This makes the metrics look like portfolio performance when they are
actually balance growth. This is not cosmetic — it can mislead users into thinking they are
generating alpha when they are simply saving aggressively.

### T2 — Multi-currency is a stub

`currency` and `fxRate` fields exist throughout the data model and are correctly imported and
stored. But no calculation uses them. `fmt()` is hard-coded to EUR. For any user with non-EUR
assets, every number related to cost basis, realized P&L, portfolio value, and yield is wrong.

### T3 — The app is accumulation-only

The data model, forecasting engine, risk framework, and UX are all designed for the "save and
grow" phase. There is no model for spending, withdrawal, pension draw-down, tax optimisation
in retirement, or estate planning. This limits the 30-year use case significantly.

### T4 — legacy analytics doc and legacy report doc have become partially stale and partially inaccurate

Specific contradictions: Passive Income Projection is listed as "Add" in legacy analytics doc but
removed per legacy report doc; `foldInto` is described as implemented in legacy report doc but has no code
path; cost basis is described as robust in legacy report doc but has oversell silent errors; gating
thresholds differ between doc (24 months) and code (12 months).

### T5 — Google Drive is a single point of failure for data durability

The entire persistence architecture depends on Google Drive AppData. No alternative storage
backend, no local-first offline guarantee, and no encryption layer. For 30-year data, this is
a serious durability risk.
