## Executive Summary

Wealth Tracker has made substantial progress since the first review cycle. Every critical
and high item from the prior pass has been addressed. The C1 rework (investment-performance
metrics now use a clean cash-flow-adjusted return series) and the decumulation engine are
particularly notable additions.

**Three new patterns now dominate:**

1. **Analytics inconsistency at the KPI layer.** The TWR, Sharpe, Sortino, Calmar, and
   volatility tiles correctly use investment-account returns; but YTD Return, Total Return,
   and CAGR still use household net-worth snapshots _without the same disclosure that they
   do_. Mixed signals in the same KPI band erode trust.

2. **Documentation has not kept pace with features.** Dark mode, decumulation planning,
   TWR/IRR analytics, strategic allocation targets, LIFO/HIFO, and named goals were all
   added after the last README update. A new user deploying from the README today would
   miss half the app's capabilities.

3. **Accessibility and chart reuse have moved forward again.** Expandable rows now expose
   hover feedback, chevrons, and persisted `aria-expanded` state; chart views now ship with
   linked companion data tables rather than bespoke one-off accessibility handling. The
   remaining UX debt is narrower and mostly concentrated in mobile and form polish.

The app is **production-fit for its intended audience** today. The open items below
represent quality-of-life, trust, and documentation work rather than correctness emergencies.

## Backend Engineering Review

### 2.1 Data Integrity & Correctness

**🟠 Offline account/snapshot edits are silently lost when Drive is newer.**  
`importDb()` merges only local-only transactions back after a cloud overwrite  
(`src/db/connection.ts:201–217`). Local snapshots, accounts, holdings, and settings
added offline on a second device are discarded. The conflict dialog
(`src/ui/conflictDialog.ts`) shows on pull, but once the user accepts the cloud copy
the local structural changes are gone with no recovery path.  
_Fix:_ Extend the merge step to union account/holdings IDs and pick the most-recent
snapshot per date before completing an `importDb()`.

**🟡 XIRR Newton solve has no bracketing fallback.**  
`xirr()` starts Newton-Raphson from a single `0.1` initial guess
(`src/model/insights.ts:552–570`). Non-trivial cash-flow schedules with multiple IRR
roots can silently diverge and return `null`. The "needs more data" placeholder then
appears even when a valid IRR exists.  
_Fix:_ Add a bisection pre-pass over `[-0.99, 5.0]` to bracket the root before
handing off to Newton, and expose a `confidence` flag in the result.

**🟡 Standalone FEE rows are recorded globally, not per-holding.**  
`computePD()` accumulates standalone `TxType.FEE` rows into `standaloneFees`
(`src/portfolio.ts:138–144`) but never credits them to a specific `isin`. A broker
custody fee attached to a named ISIN is indistinguishable from a portfolio-wide fee,
meaning per-holding cost-basis and performance figures exclude their own custody costs.  
_Fix:_ Allow `FEE` transactions to carry an optional `isin` field; allocate to that
position's cost basis when present.

**🟡 TAX transaction amount field is ambiguous.**  
For `TxType.TAX` rows, `computePD()` reads `tx.tax || tx.amount || 0`
(`src/portfolio.ts:135`). Brokers that encode the tax value in `amount` (rather than the
`tax` column) produce the same stored row; the code cannot distinguish and may
double-count or skip the value depending on which field was populated at import time.  
_Fix:_ Document the canonical contract for TAX rows in the importer and add a test
with a real Trade Republic `TAX_OPTIMIZATION` row.

**🟡 Import deduplication counter resets per session.**  
`buildRowId()` disambiguates same-key rows with a per-run counter suffix (`#1`, `#2`)
(`src/import/parse.ts:314–324`). If the same CSV is imported twice in separate sessions,
the counters regenerate identically, so `INSERT OR IGNORE` silently drops all rows from
the second import as apparent duplicates.  
_Fix:_ Generate disambiguation suffixes from a content hash of the full row rather than
a session-scoped counter, making IDs stable across multiple import runs.

### 2.2 Import & Parsing

**🟡 Rebalance plan fails silently when `calibrationInterval` is unset.**  
`computeRebalancePlan()` divides by `INTERVAL_PER_YEAR[calibrationInterval]`
(`src/model/drift.ts:202–205`). If the setting is missing or undefined,
`INTERVAL_PER_YEAR[undefined]` is `undefined`, and the per-execution amounts become
`NaN` with no user-visible warning.  
_Fix:_ Add a fallback to `'monthly'` and emit a console warning when the setting is
absent.

### 2.4 Technical Debt

**🟢 Settings are an untyped string bag.**  
`Settings` is `Record<string, string | null | undefined>` (`src/types.ts:89–93`). Numbers,
booleans, and enum values are coerced to strings on write and manually parsed on read. This
trades type safety for flexibility but makes settings bugs hard to catch at compile time.  
_Fix:_ Create a typed settings accessor module (e.g., `getNumberSetting(key, default)`) as
an incremental improvement; no migration needed.

**🟢 `rowId` is stored as `Number`, not `BigInt`.**  
`rowToTx` casts the SQLite `rowid` column as `Number(row[0])`
(`src/db/repositories/transactions.ts:205`). SQLite rowids are 64-bit integers; past
`Number.MAX_SAFE_INTEGER` (~9 quadrillion rows) comparisons silently lose precision. This
is not a realistic risk for a personal app today but worth noting for long-term durability.

### 3.4 Empty & Loading States

**🟡 Dividends tab has no "no dividend data" empty state.**  
`renderDividends()` checks `!!pd` but does not check whether `pd.divHist` and `pd.intHist`
are both empty (`src/views/dividends.ts:31–36`). A user who has imported only BUY
transactions sees a blank KPI grid rather than a purposeful empty state explaining why
no income appears.  
_Fix:_ Add a `div-empty` branch when `pd.divHist.length === 0 && pd.intHist.length === 0`
with copy explaining "No dividend or interest income recorded yet. These appear after
importing broker transactions that include dividend or interest rows."

**🟢 Dividend KPI labels have sparse tooltips.**  
"Gross dividends", "Tax withheld", and "Gross interest" tiles in `renderDividends()` have
fewer `infoTip()` annotations than peer analytics tiles, leaving users to infer
distinctions between dividend tax and savings interest tax.  
_Fix:_ Add `infoTip()` to each income KPI label explaining what it includes and excludes
(e.g., whether it is net or gross, and whether it covers investment vs. savings accounts).

### 3.5 Information Architecture

**🟢 "＋ Update" tab label is not self-explanatory.**  
The update tab is labeled "＋ Update" with an aria-label clarifying it is for "adding
snapshots or importing CSV" (`src/template.ts:51`). For a new user, the "＋" icon
suggests generic "add new" rather than "log data"; the original "Log" name was more
descriptive even if mislabeled.  
_Fix:_ Consider "＋ Log data" or keep the aria-label updated; a visible subtitle like
"Snapshot · Import" below the icon in the nav would remove the ambiguity.

**🟢 Form fields show errors only after submission.**  
Dialogs (`src/ui/holdingDialog.ts`, `src/ui/transactionDialog.ts`, `src/ui/accountDialog.ts`)
set `aria-invalid` only after a failed submit. There is no inline real-time hint for
format-constrained fields (e.g., ISIN must match 12-character `[A-Z]{2}[A-Z0-9]{10}`).  
_Fix:_ Add client-side `oninput` / `onblur` validation with inline error text for the
ISIN field at minimum; this is the field where typos are most common and hardest to spot.

## Wealth Management Review

### 4.1 Analytics Correctness

**🔴 YTD Return is a net-worth balance metric, not an investment-return metric, but it is
not labeled as such.**  
`ytdReturn()` calls `snapTotal()` on snapshots (`src/model/insights.ts:446, 448`), meaning
it measures the year-to-date change in _total household net worth_, including deposits,
withdrawals, and savings contributions. Its tile (`src/views/analytics.ts:206–218`) sits
alongside TWR, Sharpe, and Sortino, which now correctly use investment-only returns,
with a tooltip that says only "Return from the start of this calendar year to today."
There is no disclaimer that this is balance growth, unlike the "Total Return" and "CAGR
(balance)" tiles which carry that explicit caveat.  
_Fix:_ Either (a) implement `ytdReturnFromMonthlyReturns()` using `perfData.monthlyReturns`
for a cash-flow-adjusted YTD investment return, or (b) relabel the tile "YTD (balance)" and
add the same disclaimer info-tip as on the CAGR tile: "Measures balance growth, not
investment performance."

**🟠 Annual returns year-boundary is inconsistent across years with partial data.**  
`annualReturns()` falls back to the first snapshot of a year as the baseline for year 1 or
any year without a prior-December snapshot (`src/model/insights.ts:587–590`). This means
year 1 returns are measured over an arbitrary partial window (e.g., 7 months) while year 2
returns are measured over a full calendar year, producing incomparable percentages in the
annual-returns table.  
_Fix:_ Mark partial-year returns with a "(partial)" label in the rendered table, or add a
note in the chart explaining that the first year may cover fewer than 12 months.

**🟡 Risk-free rate is not validated against the portfolio's observed return.**  
If the user sets a risk-free rate ≥ the portfolio's annualized return, Sharpe and Sortino
go negative, which is financially correct, but no UI feedback warns that this signals the
portfolio is underperforming the risk-free benchmark. A new user may see negative Sharpe
and think it is a data error rather than a meaningful result.  
_Fix:_ Add an `infoTip()` on the Sharpe tile: if `cagrForRisk < riskFreeRate`, prepend
"Return is below risk-free rate; negative Sharpe expected."

---

### 4.2 Forecasting & Retirement Planning

**🟠 Deterministic forecast does not document sequence-of-returns risk.**  
`forecastMultiAccountSeries()` (`src/model/forecast.ts:191–221`) compounds at a fixed rate.
This is appropriate for accumulation planning, but for retirement drawdown a fixed-return
assumption materially underestimates failure risk: a 50% market decline in year 1 of
retirement depletes a 4%-rule portfolio far faster than the deterministic model predicts.
The decumulation UI shows portfolio survival dates without any caveat about this limitation.  
_Fix:_ Add a visible disclaimer on the retirement chart: "This projection uses a fixed annual
return and does not account for sequence-of-returns risk. A significant early-retirement
market decline would result in earlier portfolio depletion than shown."

**🟡 Decumulation withdrawals are shown pre-tax without disclosure.**  
`decumulationSeries()` (`src/model/forecast.ts:36–119`) models gross withdrawals. For a
European investor, capital-gains tax, withholding tax, or pension-income tax would reduce
net cash received by 15–42% depending on jurisdiction and account type. The retirement
chart shows withdrawal amounts with no indication they are pre-tax.  
_Fix:_ Add a note below the drawdown card: "Withdrawal amounts shown are pre-tax. Actual
spendable income will be lower depending on your tax situation."

**🟡 Multi-account contribution budget applies entirely to the primary investment account.**  
`_buildAccountForecastInputs()` routes the global monthly contribution budget to the primary
account only (`src/views/networth.ts:86–99`). If a user has two investment accounts but
only one is marked primary, the second receives zero contribution unless per-account
contributions are manually configured. This is not documented anywhere.  
_Fix:_ Add explanatory copy in the forecast card or Settings: "Global contribution budget
goes to your primary investment account. Configure per-account contributions in Settings
to split across multiple accounts."

**🟡 Forecast search is capped at 1200 months (100 years) without user-visible feedback.**  
`forecastMonthsToTargetMulti()` returns `null` after 1200 months
(`src/model/forecast.ts:246`). A user with very low contributions or a very high goal
will see a blank ETA rather than a "goal unreachable within 100 years" message.  
_Fix:_ When `null` is returned due to the cap, display "Beyond 100-year horizon" rather
than a blank; this is more informative than a missing value.

### 4.3 Income Analytics

**🟡 Dividend CAGR can be overstated when the history starts mid-year.**  
`dividendMetrics()` computes dividend CAGR by spanning first to last calendar year
(`src/model/insights.ts:699–714`). A portfolio started in June 2024 records a partial
2024 year at lower scale; comparing that against 2026 income over a "two-year" span
inflates the annualized growth rate because the base year has fewer months of dividends.  
_Fix:_ Use actual elapsed months from the first to last dividend date for the CAGR
denominator, or label the tile "since first dividend" with a note that partial first
years inflate the rate.

---

### 4.4 Financial Model Gaps

**🟡 Inflation is a display deflator, not a real-returns model; this distinction is not
surfaced in goal ETAs.**  
`_deflateByInflation()` divides nominal forecast values by a cumulative inflation factor
(`src/views/networth.ts`). The goal ETA countdown, however, is computed on nominal figures.
A user who mentally interprets their goal target in today's purchasing power will find the
displayed ETA understates the time needed to reach that real target.  
_Fix:_ The current approach is financially valid but needs a brief explainer: "ETAs are in
nominal terms. The chart shows real (inflation-adjusted) values for illustration only."

**🟢 Rebalancing friction is not modeled in forecasts.**  
`forecastMultiAccountSeries()` assumes zero-cost rebalancing. Bid-ask spreads, broker
commissions, and capital-gains tax triggered by rebalancing can reduce long-horizon returns
by 0.1–0.2% annually. For a 30-year accumulation this is not trivial.  
_Fix:_ Document the zero-friction assumption in the forecast card tooltip; consider an
optional friction slider for advanced users.

**🟢 Forecast horizon is not surface-configurable beyond 30 years.**  
`FORECAST_RANGE_LABELS` (`src/constants.ts:23–27`) exposes 5/10/20/30 years. Some FIRE
planning scenarios need 40-50 year projections. This is a product scope decision but worth
recording.

## Documentation Review

### 5.1 Missing Feature Coverage

**🟠 Decumulation / retirement drawdown planning is undocumented.**  
`src/views/networth.ts` implements a full retirement withdrawal simulator with Fixed,
4% SWR, and % of portfolio strategies, inflation indexing, and a depletion date estimate.
The README does not mention this feature anywhere.  
_Fix:_ Add a "Retirement planning" or "Drawdown planning" subsection under "Using the app"
documenting the three withdrawal strategies, the retirement date input, and what the
depletion date means.

**🟠 Theme toggle (dark mode) is undocumented.**  
`src/main.ts:541–572` and `src/theme.ts` implement Light / Dark / System theme cycling
persisted to localStorage. This is a visible nav button but appears nowhere in the README.  
_Fix:_ Add a brief mention in "Using the app" or the dev section: the theme button in the
top nav cycles Light → Dark → System preference.

**🟠 TWR, IRR, Sharpe, Sortino, Calmar, and the investment-performance pipeline are
undocumented.**  
The Analytics tab now displays a full risk/return stack computed on investment-account
returns with cash-flow normalization. The README mentions "dividend analytics" once but
says nothing about performance metrics or how to interpret them.  
_Fix:_ Add an "Analytics" subsection explaining: (a) Level 1 KPIs (balance metrics), (b)
Level 2 KPIs (TWR, IRR: investment performance), (c) risk metrics (Sharpe, Sortino,
Calmar, volatility, drawdown), including the minimum-history requirements.

**🟠 Strategic allocation targets and the drift / rebalance-plan workflow are
underdocumented.**  
Users can set a `targetPct` on each holding in Settings, and the Portfolio drift table uses

the README mentions "ETF breakdown" for logging; nothing explains how to configure targets
or read the drift table.  
_Fix:_ Add a "Portfolio drift and rebalancing" subsection covering: how to set target
percentages in the holding dialog, what the drift table shows (actual vs. target weight),
and how the rebalance plan amounts are derived from the calibration interval.

**🟠 Named goals are not documented.**  
`src/types.ts:103–109` and `src/views/networth.ts` implement named net-worth goals with
target amounts and dates, shown as progress cards. The README does not mention them.  
_Fix:_ Add a paragraph under "Using the app" explaining that goals can be configured in
Settings and appear on the Net Worth tab as progress cards, excluding locked accounts from
the progress calculation.

**🟠 LIFO and HIFO cost-basis methods are not documented.**  
The README "Known limitations" section (line 335) still says "FIFO and average-cost both
dequeue lots correctly." The Settings UI now exposes all four methods (avgco, FIFO, LIFO,
HIFO). This is listed as a limitation when it is actually a documented feature.  
_Fix:_ Update line 335: "The app supports four cost-basis methods: average cost (avgco),
FIFO, LIFO, and HIFO. Select your method in Settings."

## Cross-Cutting Themes

### T1: Analytics label consistency: balance metrics vs. investment metrics

The C1 rework was correct and significant. TWR, Sharpe, Sortino, Calmar, volatility, and
drawdown now correctly use investment-account-only monthly returns. However, YTD Return
still uses `snapTotal()` and sits in the same visual band without the "balance" qualifier
that Total Return and CAGR carry. The risk is that users assume all tiles in the analytics
view have the same denominator. A single label fix and one info-tip update resolves this.

### T2: Documentation lag is now the biggest discovery risk

Every major feature added since the last review cycle, including decumulation, dark mode, strategic
targets, LIFO/HIFO, goals, and the investment-performance pipeline, is absent from the README.
A developer evaluating the app from the repo page, or a returning user consulting the docs,
sees a feature set two generations behind the code. The README should be treated as part
of the definition of done for every feature PR.

### T3: Accessibility improvements now converge on shared building blocks

Keyboard accessibility, focus management, dialogs, expandable-row affordances, and chart
data-table mirrors are now handled through shared patterns rather than one-off fixes. The
remaining UX debt is smaller in scope and mostly concerns mobile tap targets, empty states,
and inline validation.
